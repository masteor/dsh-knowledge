# Автоматический перенос локализации на новые версии

Механизм, который переносит русский перевод на обновлённый upstream **без ручного
слияния 47 файлов**.

## Зачем это нужно

Плагин активно развивается (8 релизов за 13 дней). Обычное `git merge` здесь
не работает: переведённые строки и строки автора живут в одних и тех же местах,
поэтому конфликты возникают почти в каждом файле, а разрешать их вручную
по 1300 строк — бессмысленный труд.

## Как это работает

Вместо слияния — **переприменение по словарю**:

```
1. main обновляется до upstream/main        (чистое зеркало, ff-only)
2. ветка ru-localization ПЕРЕСОЗДАЁТСЯ от main
3. словарь переводов накладывается на новый код
4. правки тестовых ожиданий накладываются отдельным слоем
5. CONTRIBUTORS.md восстанавливается (его нет в upstream)
```

Словарь не зависит от версии: если автор переписал код, но строка осталась
той же — перевод применится сам.

## Состав каталога

| Файл | Что |
|---|---|
| `pairs.json` | ~1180 пар «китайский → русский»: литералы и JSX-текст |
| `test-pairs.json` | ~22 пары для тестовых ожиданий |
| `update-localization.mjs` | основной скрипт переноса |
| `extract-pairs.mjs` | пересборка словаря из разницы с upstream |
| `CONTRIBUTORS.md` | восстанавливается при переносе |
| `untranslated.txt` | что не нашлось в словаре (создаётся при запуске) |

## Запуск

```bash
cd ~/.dsh/plugin-patches/dsh-knowledge/i18n

node update-localization.mjs --dry-run   # посмотреть план
node update-localization.mjs             # перенести
node update-localization.mjs --report    # только список непереведённых строк
```

После переноса скрипт напомнит:

```bash
cd /home/user/Projects/tmp/dsh-knowledge
npm run build && npm test
git add -A && git commit && git push origin ru-localization
```

Другой репозиторий задаётся переменной:

```bash
DSH_KNOWLEDGE_REPO=/путь/к/репо node update-localization.mjs
```

## Что делать с непереведёнными строками

После прогона смотри `untranslated.txt`. Если список не пуст — автор добавил
новые строки. Порядок:

1. Перевести (вручную или субагентом — см. скилл `localize-dsh-plugin`).
2. Дописать пары в `pairs.json` (или `test-pairs.json` для тестов).
3. Запустить скрипт снова.

## Ловушки, выученные на практике

### JSX-замены только по границам тегов

Ключи словаря бывают двух видов:

- **литералы** (с кавычками): `'текст'`, `` `текст` `` — границы заданы кавычками,
  заменяются как есть;
- **JSX-текст** (без кавычек): `<h3>текст</h3>` — заменять **только** между `>`
  и `<` либо рядом со вставкой `{…}`.

Без этого ограничения короткий JSX-ключ вроде `中央日报 · 本机待上传` заменяется
**внутри** более длинной строки и даёт мешанину:

```
Центральный журнал · ожидает загрузки с этого устройства {state.sync.pending} 条{…}
```

Это та же ловушка подстрок, что и с обычным текстом, только на уровне разметки.
В коде за это отвечает `applyPairs()` — не упрощай её.

### Длинные ключи первыми

Словарь отсортирован по убыванию длины ключа. Иначе короткая пара «съест» часть
длинной. Сортировка делается при записи словаря и повторяется при загрузке.

### `lastIndex` у RegExp

При переборе нескольких файлов одним и тем же regex с флагом `g` его `lastIndex`
не сбрасывается, и часть файлов даёт 0 совпадений. Создавай новый объект regex
на каждый файл — я на этом потерял полчаса.

### Тесты не переводятся словарём UI

Тестовые ожидания — специфичные assert-строки, они обновляются **отдельным
слоем** (`test-pairs.json`). Попытка применить к ним UI-словарь ломает проверки.

### Исходники `src/` намеренно исключены

В `src/` лежат внутренние тексты ошибок, которые мы не переводим (вариант C).
Если включить их в отчёт, он вечно будет показывать ~380 «непереведённых» строк
и мешать видеть реальные пропуски.

## Проверка механизма

Механизм проверялся на симуляции: репозиторий откатывался к чистому upstream
(11 276 иероглифов в UI), затем прогонялся перенос.

| Метрика | До | После |
|---|---|---|
| Иероглифы в UI | 11 276 | ~94 |
| Иероглифы: `web/` | 0 после переноса | 0 |
| Наложено пар | — | ~1134 |
| Правок тестов | — | 21 |
| Тесты | 230/230 (чистый upstream) | **227/230** |

Остаток в 94 иероглифа — внутренние сообщения об ошибках (`worklog/central.js`)
и маркер протокола `[依据:ID]`. Оба класса переводу не подлежат.

Три оставшихся падения тестов — предсуществующие (проверка типов против
DSH-контракта и HTTPS-консоль), они есть и на чистом upstream.

## Когда механизм не справится

- Автор **переименовал или переписал** существующую строку → пара не найдётся,
  строка попадёт в `untranslated.txt`;
- Автор **изменил структуру** JSX так, что текст перестал быть отдельным узлом;
- Появились **новые файлы** — они не входят в `files`, но словарь к ним
  применится, если пути совпадают.

Во всех случаях решение одно: посмотреть `untranslated.txt`, перевести
и дописать в словарь.

## Автоматическая проверка (GitHub Actions)

Файл `.github/workflows/upstream-localization-check.yml` раз в сутки проверяет,
не вышла ли новая версия оригинального плагина.

**Что делает CI:**

1. сравнивает ветку перевода с `upstream/main`;
2. если есть новые коммиты — прогоняет перенос по словарю;
3. собирает проект и запускает тесты;
4. создаёт issue с отчётом: сколько коммитов отстаём, сколько строк надо
   перевести, прошла ли сборка, сколько тестов упало.

**Чего CI НЕ делает — и почему:**

| Не делает | Причина |
|---|---|
| Не переводит новые строки | нужен LLM-ключ в репозитории — лишняя поверхность атаки для публичного форка |
| Не пушит | в форках `GITHUB_TOKEN` имеет права только на чтение; пуш требует PAT в Secrets |
| Не дописывает словарь | машинный перевод размыл бы 1179 проверенных пар |

Автоматический перевод новых строк **намеренно оставлен человеком**: их обычно
5–20 на релиз, это несколько минут, а качество нельзя проверить автотестом —
синтаксически валидная строка может быть бессмысленной.

**Почему issue, а не PR:** issue не трогает код и не создаёт ложного ощущения,
что перевод готов. Ты видишь отчёт и решаешь, когда заняться.

**Дубли не плодятся:** workflow ищет уже открытый issue с меткой
`upstream-update` и не создаёт второй.

**Ручной запуск:** Actions → «Проверка обновлений upstream» → Run workflow.
